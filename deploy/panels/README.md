# VPN-панели

Панели развёрнуты отдельно от монорепозитория и уже работают. Этот документ —
о том, как к ним подключается бот и как ограничить к ним доступ.

| Панель | Адрес | Авторизация | Продуктовая линейка |
|---|---|---|---|
| AlexisHW/amneziawg-web-ui | `awg-de.rockfactor.ru:8080` | HTTP Basic Auth | Amnezia WG |
| PasarGuard | `ownnet.rockfactor.ru:8982/pg-panel/` | постоянный API-ключ | Vless |

## Главное: панели не должны быть доступны всему интернету

Панели хранят приватные ключи всех клиентов сервиса. Компрометация любой из них
равна компрометации всего бизнеса: злоумышленник получает доступ к трафику
покупателей и может выдавать себе конфигурации бесплатно.

Сейчас обе панели открыты на публичных адресах с нестандартными портами.
Нестандартный порт защитой не является — массовые сканеры находят такие сервисы
за часы, а автор AWG-панели прямо предупреждает в README, что Basic Auth
подбирается перебором.

Минимально необходимое: доступ только с IP сервера приложения и с вашего
административного IP.

## AWG-панель: ограничение по IP

У панели есть переменная `IP_LIST` — она подставляется в nginx внутри
контейнера как список `allow`.

```bash
docker stop awg-panel && docker rm awg-panel

docker run -d \
  --name awg-panel \
  --restart unless-stopped \
  -e NGINX_PORT=8080 \
  -e NGINX_USER=api_bot \
  -e NGINX_PASSWORD='<длинный_случайный_пароль>' \
  -e IP_LIST="ПУБЛИЧНЫЙ_IP_VPS1,ВАШ_АДМИНСКИЙ_IP" \
  -e SSL_EMAIL="admin@rockfactor.ru" \
  -e SSL_DOMAIN="awg-de.rockfactor.ru" \
  --cap-add NET_ADMIN --cap-add SYS_MODULE \
  -p 8080:8080 -p 80:80 \
  -p 51820-51830:51820-51830/udp \
  -v awg_config:/app/config \
  -v ssl:/etc/letsencrypt \
  alexishw/amneziawg-web-ui:1.8.5
```

Пароль: `openssl rand -base64 32`

Тег образа зафиксирован намеренно. У репозитория **нет файла LICENSE**, то есть
формально права на коммерческое использование не предоставлены; полагаться на
`latest` при таком статусе — лишний риск. Стоит открыть issue с просьбой
добавить MIT или Apache-2.0. Это не юридическая консультация — для окончательной
оценки нужен профильный специалист.

Порт 80 пробрасывается только ради выпуска сертификата: он даёт доступ
исключительно к `/.well-known`. В `IP_LIST` придётся добавить диапазоны
Let's Encrypt, иначе проверка не пройдёт.

## PasarGuard: ограничение через firewall

Своего вайтлиста у панели нет, поэтому ограничиваем на уровне хоста:

```bash
sudo ufw allow from ПУБЛИЧНЫЙ_IP_VPS1 to any port 8982 proto tcp
sudo ufw allow from ВАШ_АДМИНСКИЙ_IP  to any port 8982 proto tcp
sudo ufw deny 8982/tcp
sudo ufw reload
```

Порядок правил важен: `ufw` применяет первое подходящее, поэтому `allow`
должны идти до `deny`. Проверить: `sudo ufw status numbered`.

Для бота используйте **постоянный API-ключ** из `POST /api/api_key`, а не JWT
администратора: ключ не истекает, отзывается точечно и не требует хранить
пароль админа в `.env`.

## Настройки в .env

```bash
# AWG — Basic Auth, не API-ключ
AWG_API_URL=https://awg-de.rockfactor.ru:8080
AWG_API_USER=api_bot
AWG_API_PASSWORD=<пароль из NGINX_PASSWORD>
AWG_SERVER_ID=<id сервера внутри панели>

# PasarGuard — постоянный ключ
PASARGUARD_API_URL=https://ownnet.rockfactor.ru:8982/pg-panel
PASARGUARD_API_KEY=<ключ из POST /api/api_key>
```

`AWG_SERVER_ID` берётся из `GET /api/servers` — это идентификатор интерфейса
внутри панели, не путать с идентификатором клиента.

## Идемпотентность выдачи

Ни одна из панелей не поддерживает `Idempotence-Key` — в отличие от ЮКассы.
При повторе запроса после таймаута создастся дубль клиента, а значит, лишний
конфиг и расхождение с базой.

Решение на стороне бота — детерминированное имя клиента:

```
tg_{user_id}_{sub_id}_d{device_no}

# пример: tg_123456789_42_d1, tg_123456789_42_d2
```

Перед созданием проверяем существование по этому имени. При истечении, продлении
и отзыве работаем по префиксу `tg_{user_id}_{sub_id}_`.

## Соответствие операций

| Событие | AWG-панель | PasarGuard |
|---|---|---|
| Выдать конфиг | `POST /api/servers/{sid}/clients` — конфиг в ответе | `POST /api/user` + ссылка-подписка |
| Заблокировать при истечении | `POST .../suspend` | `PUT /api/user/{username}` со статусом |
| Разблокировать при продлении | `POST .../activate` | то же |
| Плановое отключение | `PUT .../suspend-time` | нативный `expire` |
| Отозвать | `DELETE .../clients/{cid}` | `DELETE /api/user/{username}` |

Важная деталь AWG-панели: снятие `suspend_at` **не реактивирует** клиента
автоматически — это поведение задокументировано в CHANGELOG 1.7.1. После
продления всегда вызывайте `POST .../activate` явно.

## Бэкап конфигурации панелей

Состояние AWG-панели хранится в JSON-файле, а не в БД. Том с конфигурацией
обязательно монтировать наружу и включать в резервное копирование:

```bash
curl -u api_bot:ПАРОЛЬ https://awg-de.rockfactor.ru:8080/api/config/export \
     > awg_backup_$(date +%F).json
```

Поставьте это в cron рядом с бэкапом PostgreSQL.

## Проверка изоляции

С постороннего хоста — не с VPS-1 и не со своего рабочего места:

```bash
curl -m 5 -I https://awg-de.rockfactor.ru:8080/
curl -m 5 -I https://ownnet.rockfactor.ru:8982/pg-panel/
```

Обе команды должны отваливаться по таймауту или отдавать 403. Если возвращается
форма входа — ограничение не работает.

## Открытые вопросы

**Лицензия AWG-панели.** Файла LICENSE нет, то есть по умолчанию «все права
защищены». Для сервиса, принимающего платежи, это реальный юридический риск.
До прояснения — фиксировать тег образа и держать форк.

**AGPL-3.0 у PasarGuard.** Копилефт распространяется на сетевое использование.
Пока панель используется как есть, без правок исходников, а бот общается с ней
по HTTP как отдельный процесс, обязательств раскрывать код бота не возникает.
Модифицировать панель без юридической проверки не стоит.
