# AmneziaWG-панель — развёртывание для OwnNetBot

Панель `AlexisHW/amneziawg-web-ui` для линейки «Amnezia WG». Клиенты
подключаются **напрямую** к серверу в Грузии; промежуточных релеев
в российской юрисдикции в схеме нет.

## Инфраструктура

| Роль | Сервер | Адрес | Домен |
|---|---|---|---|
| Бот и сайт | VPS-1, Beget SPB | `217.114.2.219` | `своясеть.рокфактор.рф` |
| **Панель + WireGuard** | Грузия | `144.31.246.234` | `ge01awg.rockfactor.ru` |

```
   клиент ──UDP 51820 (AmneziaWG)──→ [ панель GE ]
                                   ge01awg.rockfactor.ru
                                              │
   админ ──WG 51900──→ 10.10.0.0/24 ──→ [ nginx 443 ] ──┤
                                              │
   бот ──TLS через интернет──→ 217.114.2.219 ──────────┘
```

---

## Почему в схеме больше нет каскада через РФ

Раньше клиентский трафик шёл через релей `on.rockfactor.ru` (1Gb.ru, Москва),
который DNAT-ом пробрасывал UDP 51821 → 51820 в Грузию. **Схема выведена
из эксплуатации: трафик к релею заблокирован.**

Причина не в самом релее, а в том, что он ничего не маскировал:

- `DNAT` + `MASQUERADE` — это ядерный NAT. Он подменяет адреса в IP-заголовке
  и не трогает полезную нагрузку. Между клиентом и релеем, то есть целиком
  внутри российского сегмента, шёл **обычный WireGuard**.
- Обычный WireGuard тривиально опознаётся по сигнатуре. Пакет инициализации —
  всегда ровно 148 байт, ответ — 92 байта, первый байт равен типу сообщения
  (`0x01`/`0x02`/`0x03`/`0x04`), следом три нулевых зарезервированных байта.
  Фиксированная длина плюс константа в начале — это правило DPI в одну строку,
  и оно давно применяется на ТСПУ.
- Промежуточный хост при этом добавлял к схеме три минуса: единая точка отказа
  (падает релей — отключены все клиенты), потолок пропускной способности
  на его канале и подмена источника, из-за которой панель видела все
  подключения с одного адреса.

Вывод, который зашит в текущую схему: **маскировка должна быть на уровне
протокола, а не на уровне маршрута.** Этим занимается обфускация AmneziaWG
(раздел ниже), и она в этой конфигурации не опция, а обязательный элемент —
прикрыться промежуточным узлом больше нечем.

Что это меняет практически:

| | Было (через каскад) | Стало (прямое подключение) |
|---|---|---|
| Endpoint в `.conf` | `on.rockfactor.ru:51821` | `ge01awg.rockfactor.ru:51820` |
| Порт 51820/udp на панели | только с IP релея | открыт всем |
| Реальные IP клиентов в панели | не видны (MASQUERADE) | видны |
| Точки отказа | релей + панель | панель |
| Ротация обфускации | правило DNAT на релее под каждый порт | правило `ufw` на панели |

Отдельный риск, который теперь надо держать в голове: **IP сервера панели
открыт клиентам напрямую**, и его блокировка отключит линейку целиком.
Поэтому `Endpoint` в конфигурациях — доменное имя, а не IP (см. шаг 6):
смена адреса решается A-записью, без перевыдачи конфигов всем клиентам.

## Отличие от PasarGuard: панель закрывается целиком

У PasarGuard путь `/sub/` обязан быть публичным — клиенты открывают ссылку
со своих устройств. У AmneziaWG этого нет: конфигурация приходит файлом
в Telegram, а подключение идёт по UDP напрямую к WireGuard. **В веб-панель
клиенты не обращаются никогда.**

Поэтому вайтлист на HTTP-доступ вешается на весь сервер: только публичный IP
VPS-1 и админский туннель. Разделение по путям не нужно.

Публично открыт только UDP-порт самого WireGuard — веб-морда и API к нему
отношения не имеют.

Basic Auth панели при этом остаётся включённым как второй рубеж — автор
проекта прямо предупреждает в README, что одного Basic Auth недостаточно
и он подбирается перебором.

## Шаг 0. DNS

| Запись | Значение | TTL |
|---|---|---|
| `ge01awg.rockfactor.ru` A | `144.31.246.234` | 300 |

Низкий TTL — осознанное решение: этот адрес теперь стоит в клиентских
конфигурациях, и при блокировке IP переезд должен занимать минуты.
Записи `on.rockfactor.ru` в зоне быть не должно.

Проверка с сервера панели:

```bash
dig +short A ge01awg.rockfactor.ru
dig +short A on.rockfactor.ru        # ожидаем пусто
curl -s https://api.ipify.org
```

```bash

ufw default deny incoming
ufw default allow outgoing
```

**Порт WireGuard открыт всем** — клиенты приходят напрямую:

иначе оно будет вводить в заблуждение при разборе доступов:

```bash
ufw status numbered | grep 81.177.48.224
ufw delete allow from 81.177.48.224 to any port 51820 proto udp
```

## Шаг 2. Админский WireGuard

Тот же скрипт, что для PasarGuard:

```bash
cd /tmp
git clone https://github.com/rockfactor/onbot_site.git onbot
cd onbot/deploy/panels/pasarguard
sudo bash setup-admin-wg.sh
```

**Важно: на вопрос о порте укажи `51900`, а не значение по умолчанию.**
Панель публикует диапазон `51820–51830/udp` под клиентские интерфейсы,
и админский туннель на `51830` столкнётся с ним.

```bash
ufw allow 51900/udp
ufw --force enable
```

Конфигурация для телефона:

```bash
sudo qrencode -t ansiutf8 < /etc/wireguard/clients/device2.conf
```

Админский туннель — обычный WireGuard без обфускации. Это допустимо: им
пользуешься ты, из-под нужного тебе канала, и его блокировка не затрагивает
клиентов. Если админский доступ понадобится из РФ и порт 51900 перестанет
отвечать — поднимай админский интерфейс тоже в панели, с обфускацией.

## Шаг 3. Запуск панели

```bash
PANEL_PASS="$(openssl rand -base64 32)"
echo "Пароль панели: $PANEL_PASS"   # сохранить в менеджер паролей

docker run -d \
  --name awg-panel \
  --restart unless-stopped \
  -e NGINX_USER=api_bot \
  -e NGINX_PASSWORD="$PANEL_PASS" \
  -e AUTO_START_SERVERS=true \
  -e DEFAULT_MTU=1280 \
  --cap-add NET_ADMIN --cap-add SYS_MODULE \
  -p 127.0.0.1:8080:80 \
  -p 51820-51830:51820-51830/udp \
  -v awg_config:/app/config \
  alexishw/amneziawg-web-ui:1.8.5
```

Разбор ключевых решений:

**`-p 127.0.0.1:8080:80`** — панель доступна только с самого сервера.
Наружу её выставляет наш nginx, он же ограничивает доступ. Без привязки
к loopback порт был бы открыт в обход вайтлиста.

**`-p 51820-51830:51820-51830/udp`** — UDP-диапазон публикуется на всех
интерфейсах, это и есть точка входа клиентов. Наружу через `ufw` открыт
только `51820`; остальные порты диапазона понадобятся при ротации
обфускации и открываются по мере создания интерфейсов.

**`SSL_EMAIL` и `SSL_DOMAIN` не задаём.** Встроенный certbot панели занял бы
порт 80 и подрался с нашим nginx. TLS терминируем снаружи.

**`IP_LIST` не используем.** Вайтлист внутри контейнера видит адреса через
Docker-сеть, а не реальные источники. Ограничение на уровне хоста надёжнее
и проверяемо.

**Тег `:1.8.5` зафиксирован.** У репозитория нет файла LICENSE — см. раздел
про лицензию ниже.

Проверка:

```bash
docker ps
ss -tlnp | grep 8080     # должно быть 127.0.0.1:8080, не 0.0.0.0:8080
ss -ulnp | grep 51820    # должно быть 0.0.0.0:51820
curl -su api_bot:"$PANEL_PASS" http://127.0.0.1:8080/api/servers
```

## Шаг 5. Создание сервера AWG в панели

Подключись к админскому WireGuard, открой `https://ge01awg.rockfactor.ru/`,
войди под `api_bot` и созданным паролем.

Создай сервер: порт `51820`, подсеть `10.0.0.0/24`, MTU `1280`,
**обфускация включена — обязательно.** Интерфейс без обфускации в этой схеме
не запускаем вообще: это ровно тот трафик, из-за которого пришлось отказаться
от прежней схемы.

Параметры обфускации генерируются модулем `vpn_api/awg_obfuscation.py` —
он проверяет ограничения протокола до отправки в панель:

```bash
python -c "
from vpn_api.awg_obfuscation import generate_server_params, packet_sizes
p = generate_server_params()
print(p.as_dict())
print(packet_sizes(p))
"
```

Значения по умолчанию из UI панели не используем: они одинаковы у всех, кто
поднял ту же панель, и опознаются так же легко, как штатный WireGuard.

Затем узнай идентификатор сервера — он понадобится боту:

```bash
curl -su api_bot:ПАРОЛЬ https://ge01awg.rockfactor.ru/api/servers | python3 -m json.tool
```

Значение поля `id` пойдёт в `AWG_SERVER_ID`.

### Мультисервер

Панель умеет держать несколько интерфейсов в одном контейнере. Тарифы
1/3/5 устройств можно развести по разным подсетям и портам — теперь это
дешевле, чем раньше: достаточно открыть порт в `ufw` на самой панели,
согласовывать правила с промежуточным узлом больше не нужно.

```bash
ufw allow 51821/udp     # под новый интерфейс awg1
```

На старте всё равно проще один сервер.

## Шаг 6. Подключение к боту

В `/opt/ownnetbot/.env` на VPS-1:

```bash
AWG_API_URL=https://ge01awg.rockfactor.ru
AWG_API_USER=api_bot
AWG_API_PASSWORD=<пароль из шага 3>
AWG_SERVER_ID=<id из шага 5>
```

Панель работает на HTTP Basic Auth, а не на API-ключе — для `aiohttp`
это `auth=aiohttp.BasicAuth(user, password)`.

Приватной сети с Грузией нет, поэтому запросы идут через интернет.
Защищает их TLS, а доступ ограничен вайтлистом по публичному IP VPS-1.

Проверка:

```bash
curl -su api_bot:ПАРОЛЬ https://ge01awg.rockfactor.ru/api/servers
```

### Подмена Endpoint: домен вместо IP

Панель генерирует `.conf` с адресом самого сервера — `144.31.246.234:51820`.
Клиенту в конфигурацию должен попасть **домен**, а не этот IP.

В таблице `vpn_nodes` у ноды заполняется поле:

```
client_endpoint = 'ge01awg.rockfactor.ru:51820'
```

Зачем, если адрес тот же самый: конфигурация живёт у клиента месяцами.
Если IP попадёт в блокировку, с доменом достаточно поменять A-запись —
клиент подхватит новый адрес при следующем поднятии интерфейса. С зашитым
IP пришлось бы перевыпускать конфигурации всем активным подписчикам.

Оговорка: WireGuard резолвит `Endpoint` **один раз, при старте интерфейса**.
Пользователю после переезда нужно выключить и включить подключение —
это стоит держать в шаблоне сообщения поддержки.

`AmneziaWGAdapter` получает конфигурацию одним запросом
`POST /api/servers/{sid}/clients` и переписывает строку `Endpoint`
**только внутри секции `[Peer]`** — в `[Interface]` лежат параметры
обфускации, трогать их нельзя. Если `Endpoint` не найден или найден дважды,
адаптер падает с ошибкой: лучше не выдать конфигурацию, чем выдать сломанную.

Механизм остаётся и на будущее: добавление новой ноды или запасного адреса —
строка в БД, без правок кода.

`PersistentKeepalive = 25` оставляем: он нужен для NAT на стороне клиента —
домашние роутеры и мобильные операторы убирают запись из conntrack за пару
минут простоя.

## Обфускация: что хранить и как менять

Теперь это единственный слой маскировки, поэтому раздел стоит читать
внимательнее остальных.

### Что именно ломается для DPI

| Параметры | Что делают |
|---|---|
| `Jc`, `Jmin`, `Jmax` | `Jc` мусорных пакетов случайной длины `Jmin..Jmax` **до** рукопожатия — ломают счёт пакетов и их размеры |
| `S1`, `S2` | добавляют мусор в пакеты инициализации (148 + `S1`) и ответа (92 + `S2`) — ломают фиксированную длину |
| `S3`, `S4` | префиксы cookie-пакета и пакетов данных (AWG 2.0) |
| `H1`–`H4` | заменяют штатные типы сообщений `1`–`4` на случайные 32-битные значения — ломают сигнатуру первого байта |

Ограничения протокола, которые проверяет `validate_server_params()`:

- `S1 ≤ 1132`, `S2 ≤ 1188` (потолок MTU 1280);
- **`S1 + 56 ≠ S2`** — иначе размеры init и response совпадут, и DPI снова
  видит пару пакетов одинаковой длины;
- `S3 ≤ 64`, `S4 ≤ 32`;
- `H1`–`H4` в диапазоне `5..2147483647` и **попарно различны** — значения
  `1`–`4` заняты штатными типами WireGuard;
- `Jmin < Jmax ≤ 1280`, `Jc` в пределах `1..128` (рекомендуемо `4..12`).

### Разделение параметров

| Группа | Параметры | Можно ли менять |
|---|---|---|
| Общие | `S1`–`S4`, `H1`–`H4` | **нет**, после выдачи первого конфига |
| Клиентские | `Jc`, `Jmin`, `Jmax` | да, генерируются на каждую выдачу |

Общие параметры участвуют в разборе рукопожатия: расхождение хотя бы
в одном значении между сервером и клиентом — соединение не устанавливается.
Клиентские управляют мусорными пакетами до рукопожатия, сервер их игнорирует,
поэтому у каждого клиента может быть свой профиль. Именно это мешает
построить одно правило DPI на весь сервис.

Сгенерированные `ServerParams` сохраняются в `vpn_nodes` рядом
с `client_endpoint` — чтобы знать, какой интерфейс какими значениями настроен,
и уметь воспроизвести конфигурацию при восстановлении.

### Ротация без обрыва

Менять `S1`–`S4` и `H1`–`H4` на работающем интерфейсе нельзя: все ранее
выданные клиенты отвалятся разом.

Если DPI начнёт распознавать текущий профиль, порядок такой:

1. Создать новый интерфейс `awg1` со свежими параметрами через мультисервер
   панели — на другом порту и в другой подсети.
2. Открыть новый порт: `ufw allow 51821/udp`.
3. Переключить выдачу новых клиентов на `awg1` — в `vpn_nodes` пометить
   `awg0` неактивным для новых выдач, но оставить работающим.
4. Дождаться истечения подписок на `awg0`.
5. Удалить `awg0` и закрыть его порт: `ufw delete allow 51820/udp`.

Так замена проходит постепенно, без единовременного отключения всех.

## Вывод релея `on.rockfactor.ru` из эксплуатации

Порядок важен: сначала открываем прямой путь, потом переводим клиентов,
и только затем гасим релей.

1. **Открыть прямой доступ на панели** (шаг 1):
   `ufw allow 51820/udp`, снять правило для `81.177.48.224`.
2. **Проверить, что порт отвечает снаружи** — с постороннего хоста:
   `nc -u -z -w3 ge01awg.rockfactor.ru 51820` (для UDP надёжнее просто
   поднять тестовый клиент с новой конфигурацией).
3. **Обновить `client_endpoint`** у ноды в `vpn_nodes`
   на `ge01awg.rockfactor.ru:51820`. С этого момента новые выдачи уходят
   уже с правильным адресом.
4. **Перевыпустить конфигурации активным клиентам.** Это неизбежно: в уже
   выданных `.conf` зашит `on.rockfactor.ru:51821`, и они перестанут работать.
   Выдача идёт тем же путём, что и обычная, — имя клиента детерминировано
   (`tg_{user_id}_{sub_id}_d{device_no}`), поэтому старого клиента в панели
   нужно удалить и создать заново, а файл отправить пользователю в бота
   с пояснением, что старый профиль надо удалить в приложении.
5. **Убрать A-запись** `on.rockfactor.ru` из зоны.
6. **Погасить сервер** на 1Gb.ru и отключить тариф.

Пока пункт 4 не выполнен, релей не выключаем — иначе клиенты останутся
без связи до перевыдачи.

## Проверка изоляции

С постороннего хоста — не с VPS-1 и не из-под WireGuard:

```bash
curl -m 5 -o /dev/null -w 'панель      %{http_code}\n' https://ge01awg.rockfactor.ru/
curl -m 5 -o /dev/null -w 'API         %{http_code}\n' https://ge01awg.rockfactor.ru/api/servers
curl -m 5 -o /dev/null -w 'порт 8080   %{http_code}\n' http://144.31.246.234:8080/
```

| Проверка | Ожидание |
|---|---|
| панель, API | `403` |
| порт 8080 | таймаут |
| форма входа | не должна появляться |
| UDP 51820 | отвечает — это клиентский вход, так и задумано |

Если видишь окно Basic Auth — вайтлист не работает. Разбираться до того,
как заводить клиентов.

## Обслуживание

### Бэкапы

**Состояние панели хранится в JSON-файле, не в базе.** Том с конфигурацией
обязательно включать в резервное копирование — его потеря означает, что все
выданные ключи перестают работать.

```bash
# Полный экспорт через API
curl -su api_bot:ПАРОЛЬ https://ge01awg.rockfactor.ru/api/config/export \
     > /root/awg_backup_$(date +%F).json

# Плюс сам том Docker
docker run --rm -v awg_config:/data -v /root:/backup alpine \
    tar czf /backup/awg_volume_$(date +%F).tar.gz /data
```

Поставь в cron и выгружай копии в S3.

### Мониторинг доступности

Прямое подключение означает, что блокировка адреса панели видна не сразу —
бот продолжит выдавать конфигурации, которые не работают. Минимальная
проверка с российского хоста (VPS-1) по крону:

```bash
nc -u -z -w3 ge01awg.rockfactor.ru 51820 && echo ok || echo BLOCKED
```

UDP-проверка не даёт стопроцентной достоверности, поэтому надёжнее держать
на VPS-1 тестовый клиентский конфиг и раз в час поднимать интерфейс
с проверкой рукопожатия (`wg show` → `latest handshake`).

### Обновление

Тег зафиксирован намеренно. Перед обновлением сделай бэкап и меняй версию
осознанно:

```bash
docker pull alexishw/amneziawg-web-ui:НОВАЯ_ВЕРСИЯ
docker stop awg-panel && docker rm awg-panel
# повторить docker run с новым тегом
```

После обновления проверь, что порт 8080 по-прежнему привязан к `127.0.0.1`,
а `51820/udp` — нет.

### Особенности панели

Из CHANGELOG 1.7.1: снятие `suspend_at` **не реактивирует клиента
автоматически** — это сделано намеренно. После продления подписки всегда
вызывай `POST .../activate` явно, иначе клиент останется заблокированным.

Помесячной статистики трафика по клиенту нет, есть только текущие счётчики
пиров. Для биллинга по трафику пришлось бы снимать
`GET /api/servers/{sid}/traffic` по крону и складывать дельты в Postgres.

Зато после отказа от каскада в счётчиках снова видны реальные адреса
клиентов — раньше `MASQUERADE` показывал все подключения с одного IP.
